## 1. 评估维度

每个来源按六个维度评估。**这六项彼此独立，不可互相推导：**

| 维度 | 问题 |
|---|---|
| **D1 文档** | 是否有公开、稳定、可引用的 API 文档？ |
| **D2 认证** | 需要什么凭据？如何安全存储？ |
| **D3 技术可访问** | 接口**技术上**能否被第三方桌面应用调用？ |
| **D4 授权** | 服务条款/许可**是否允许**这种调用？ |
| **D5 播放权限** | 解析出的音频流是否被授权播放？有效期多久？ |
| **D6 限制** | 配额、限流、地区限制、客户端限制 |

> ⚠️ **D3 与 D4 是两回事。** 一个接口能调通，不代表被允许调用。
> 本表把两者分列，**禁止用 D3 的结果去填充 D4**。

## 3. Navidrome / Subsonic

### 3.1 前置区分

Navidrome 提供**两套**接口，本设计**只以其中一套为基线**：

| 接口 | 说明 | 本设计是否采用 |
|---|---|---|
| **Subsonic 兼容 API** | Navidrome 实现的 Subsonic 协议子集，有公开稳定的上游文档 | ✅ **第一版基线** |
| Navidrome 自有 API | Navidrome 自己的、仍在演进的接口 | ❌ 不采用（N5） |

**【推断】** 选择 Subsonic 兼容接口的理由：它是公开文档化的稳定协议，
且多家服务器实现共享，适配器可复用于非 Navidrome 的兼容服务器。
代价是可能无法使用 Navidrome 的特有能力——这是可接受的权衡。

### 3.2 协议概述

| 维度 | 结论 | 证据 |
|---|---|---|
| D1 文档 | **【公开文档】** Subsonic API 是公开的、有版本号的 REST 风格接口 | 需核实版本号 |
| D2 认证 | **【公开文档】** 通过请求参数传递用户名与令牌/盐值 | 需核实细节 |
| D3 技术可访问 | **【公开文档】** 设计上即可被任意 HTTP 客户端调用 | 需核实 |
| D4 授权 | **【待核实】** Navidrome 服务端本身是自建服务，**用户对自己服务器的访问**；但需确认其条款对客户端类型无限制 | Navidrome 是开源自建服务 |
| D5 播放权限 | **【推断】** 内容来自用户自己的服务器与自己的音乐文件，不存在第三方版权授权问题 | 基于自建服务的性质 |
| D6 限制 | **【待核实】** 限流策略取决于服务端配置 | 需核实 |

> **D4/D5 的说明：** Navidrome 是用户**自行部署、管理自己音乐库**的服务。
> 访问自己的服务器不涉及第三方内容授权。但这**不意味着**可以忽略其服务端配置的
> 访问策略——用户仍可主动限制某客户端的访问。

### 3.3 接口映射（**全部待核实**）

> ⚠️ **下表基于公开 Subsonic API 的一般形态整理，本会话未联网拉取官方文档原文。
> 所有方法名、参数名、字段名在实施前必须逐项对照官方文档核实。**
> 表中任何一项都**不得**直接作为实现依据。

| 用途 | 拟用方法 | 关键参数 | 状态 |
|---|---|---|---|
| 连通性与版本探测 | `ping` | — | **【待核实】** |
| 曲目搜索 | `search3` | 查询串、各类结果数量上限、偏移 | **【待核实】** |
| 单曲详情 | `getSong` | 曲目 ID | **【待核实】** |
| 专辑详情 | `getAlbum` | 专辑 ID | **【待核实】** |
| 艺术家详情 | `getArtist` | 艺术家 ID | **【待核实】** |
| 播放解析 | `stream` | 曲目 ID、可选码率/格式 | **【待核实】** |
| 媒体库列表 | `musicFolders` | — | **【待核实】** |

**认证参数**【公开文档，需核实】：请求通常携带
`u`（用户名）、`t`（令牌）、`s`（盐值）、`v`（协议版本）、`c`（客户端标识）、`f`（响应格式）。
令牌一般由 `md5(密码 + 盐值)` 得到，而非直接传密码。

**实施前的核实清单：**

| # | 待核实 | 为什么重要 |
|---|---|---|
| S-1 | 官方文档的当前版本号与 URL | 所有映射的依据 |
| S-2 | `search3` 的完整参数与响应字段名 | 直接决定元数据映射 |
| S-3 | `stream` 的返回形态：是重定向、还是直接流 | 决定 URL 校验策略（重定向需逐跳校验） |
| S-4 | 认证参数的确切名称与令牌构造算法 | 认证实现的基础 |
| S-5 | 错误码的完整列表与语义 | 决定错误映射表 |
| S-6 | **Navidrome 实际实现了哪些方法** | 协议定义了 ≠ 每个实现都支持 |
| S-7 | Navidrome 对 `stream` 的 URL 有效期策略 | 决定是否可缓存播放地址 |
| S-8 | 服务端是否有默认限流 | 决定重试策略 |
| S-9 | 各版本间 `search` / `search2` / `search3` 的差异与弃用状态 | 避免使用已弃用接口 |

### 3.4 错误处理映射（**待核实**）

**【公开文档，需核实】** Subsonic 的错误通过响应体中的状态字段与错误对象表达，
而非仅靠 HTTP 状态码。这意味着：

- **HTTP 200 + 响应体标记失败** 是可能的
- 因此**不能**只看 HTTP 状态码判断成功

| 拟映射 | 对方语义 | 本项目错误 |
|---|---|---|
| 认证类错误码 | 用户名/密码错误 | `MusicSourceError::AuthFailed` |
| 令牌不被支持 | 需改用其他认证方式 | `MusicSourceError::AuthFailed`（附说明） |
| 未授权类错误码 | 账号无权访问该资源 | `MusicSourceError::Forbidden` |
| 未找到类错误码 | 资源不存在 | `MusicSourceError::NotFound` |
| 协议版本不匹配 | 客户端/服务端需升级 | `MusicSourceError::InvalidResponse` |
| HTTP 429 | 限流 | `MusicSourceError::RateLimited` |
| HTTP 5xx | 服务端错误 | `MusicSourceError::ServerError` |

> 具体错误码数值 **【待核实】** S-5，此表刻意不填数字。

### 3.5 兼容性差异（**待核实**）

不同服务器实现同一协议时可能存在差异。**实施前必须确认：**

- Navidrome 对未知方法的响应是错误还是空结果
- 字段缺失时是省略字段还是返回 null
- 分页参数是否被支持，还是被静默忽略
- 时间戳、时区、编码的处理差异

**设计应对：** 适配器必须**容忍缺失字段**，把无法解析的部分降级为 `null`
而不是整体失败。响应解析必须严格校验形状，形状不符时返回
`InvalidResponse` 而非panic或静默产生错误数据。

## 4. 技术可访问 ≠ 法律授权

本节单独成节，因为它是最容易被混淆的一点。

| 陈述 | 是否成立 |
|---|---|
| "这个接口能返回 JSON" | 技术事实 |
| "所以我可以用它" | ❌ **不成立**，是两个独立命题 |
| "Subsonic 协议是公开的" | 技术事实 |
| "所以任何 Subsonic 服务器都允许我连接" | ❌ **不成立** —— 服务器所有者的策略决定 |
| "Navidrome 是开源的" | 技术事实 |
| "所以我可以连接别人的 Navidrome" | ❌ **不成立** —— 只能连接**用户自己**的服务器 |

**本模块的定位：**
`NavidromeMusicSource` 服务于**用户连接自己的自建服务器**这一场景。
不提供、不鼓励、不设计用于连接他人服务器的能力。

**GD Studio 的定位：**
在其 D4（授权）与 D5（播放权限）取得可靠证据前，**不进入实现**。
不因"技术上可能可以调用"而推进。
